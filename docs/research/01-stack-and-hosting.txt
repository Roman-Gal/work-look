Stack and hosting decisions
Original analysis: 2026-11-20.
Chosen UI: Symfony UX + Twig; Angular was rejected. Chosen host: MyDevil MD2.
Current code/state: ../../README.md, ../architecture.txt, ../mydevil-deployment.txt.
The initial local SQLite plan has been superseded by one shared PostgreSQL on
MyDevil, accessed locally through SSH. Search remains user-triggered; cron manages
the queue worker, not autonomous searches.

1. Language and backend

PHP with Symfony fits HTTP integration, normalization, storage, background jobs
and LLM APIs. Local model training is outside this project.

Option               Suitable focus                       Project trade-off
PHP + Symfony        Familiar PHP and SaaS business logic  Fits services and workers.
Python + FastAPI     ML/data-processing focus             Auth/ORM/queue need assembly.
TypeScript + NestJS  Primarily TypeScript projects         Valid alternative, not selected.

This is an engineering fit assessment, not a framework performance benchmark.
An agent does not inherently require Python. A separate Python worker can be added
later for a concrete ML/document dependency.

Baseline: Symfony 7.4 LTS, PHP >=8.2. The release schedule checked during research
listed bug fixes through November 2028 and security fixes through November 2029.
Use an appropriate PHP 8.4 patch for hosting. Local PHP CLI was 8.2.8.
Docker is optional locally; MyDevil deployment is native.
https://symfony.com/releases

2. First-version architecture

One modular Symfony application and database, with separate worker processes using
the same code. Modules: Ingestion, Matching, Cv, Reporting and Identity. Messages
and adapters allow later extraction into services if actual needs justify it.

Components:
- HttpClient: upstream job sources and LLM APIs.
- Doctrine ORM/migrations/PostgreSQL: jobs, profiles, CV versions and reports.
- Messenger/Doctrine: database-backed queue and failure transport.
- Lock and system cron: bounded worker management; no autonomous search schedule.
- Validator/Serializer: DTO and AI-response validation; Monolog: diagnostics.

Redis/RabbitMQ are not required for the first version. Consider transport changes
after measuring load. Tasks must remain idempotent regardless of transport.
https://symfony.com/doc/7.4/messenger.html
https://symfony.com/doc/7.4/scheduler.html
https://symfony.com/doc/7.4/http_client.html

3. Symfony UX and Twig

Symfony controllers render vacancies, filters, profiles and CV previews through
Twig. Symfony Forms/Validator handle input. Add UX components where needed:
Turbo for partial updates, Stimulus for browser behavior, and potentially Live
Components for server reactivity. Current code disables full Turbo Drive navigation
to keep per-document CSP nonces aligned; progress uses Turbo Frames.

UI/backend share services in one application. A REST API for every page is not
needed; add JSON endpoints for concrete component/integration needs.
External job API requests stay in backend workers. AssetMapper/importmap avoids a
separate frontend development server.
https://symfony.com/doc/7.4/templates.html
https://ux.symfony.com/

4. Local work and ngrok

Outgoing API requests need no ngrok. A tunnel is useful for viewing the local UI
from another device:
 Browser -> ngrok HTTPS -> localhost:8000 -> Symfony controllers/Twig/UX assets
 Symfony worker -> external job API/RSS
 Local Symfony app -> SSH database tunnel -> shared MyDevil PostgreSQL

Use one Symfony origin, server-side sessions and CSRF for state-changing forms.
Configure trusted proxies/hosts and HTTPS headers explicitly.
An optional tunnel command after the local service starts:
  ngrok http 8000
Port 8000 was tested during the initial research; that research did not start a
tunnel. Configure the proxy/environment/HTTPS cookie before external access.
Personal CVs require application login or suitable tunnel access restrictions.
Never expose PostgreSQL or the debug profiler through the tunnel; PDFs need owner checks.
https://ngrok.com/docs/start
https://ngrok.com/docs/gateway/traffic-policy/actions/oauth

5. Hosting

MyDevil MD2 is the shared host for WorkLook and the Telegram bots.
See ../hosting.txt for dated limits and the reference screenshot.
PHP, PostgreSQL, SSH and cron were confirmed. Deployment uses native provider tools,
a public/ web root, private CV storage and a separately managed CLI worker.
Docker/Compose support was not confirmed and is not a production dependency.

Local Docker Compose would require a suitable environment, such as WSL2 on Windows,
and remains optional. Twig/UX assets ship with Symfony; WorkLook needs no Node build.
Keep database hosts, paths and secrets in configuration.
A deployment includes code/dependencies, private configuration, assets, migrations,
database/private-file recovery and verified worker restart.
Current deployment/migration has completed; do not treat this original plan as a
pending instruction to repeat it.
