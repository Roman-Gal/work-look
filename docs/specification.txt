Agent 2 specification: Job Search for Poland and CV Preparation
Recorded 2026-11-20. Implementation was authorized; the MVP is in this repository.

Later owner decisions take precedence over the original proposal below:
- Symfony 7.4 LTS + Symfony UX/Twig; no Angular.
- A user button starts a bounded AI agent that chooses queries and API/RSS tools.
- No autonomous scraper or scheduled searches in this phase.
- One shared PostgreSQL on MyDevil for hosted/local development via SSH; native workers.
- Actual implementation and limits: ../README.md and architecture.txt.
The original specification describes future direction, not a checklist of finished features.

1. Purpose and architecture

A private service/agent pipeline, potentially evolving into a multi-user pet project
or SaaS, gathers Polish-market vacancies, filters them against user requirements,
prepares vacancy-specific CVs without inventing facts, and produces a report.
Regular autonomous collection was part of the original proposal; the current
user-triggered workflow supersedes that scheduling assumption.

2. Proposed modules

Independent modules/workers communicate through a task queue and relational storage:
- Ingestion: adapters for JustJoinIT, NoFluffJobs, Pracuj.pl, Bulldogjob, The Protocol
  and others. Scheduled collection belongs to the original future proposal.
- PostgreSQL storage:
  users/user_profiles: structured canonical CV (JSON/Markdown), desired salary,
  work mode, starting address/location, languages and filter criteria.
  job_sources/jobs: source + external_id or URL identity, raw payload, normalized
  fields and processing status.
  job_matches: relevance score/explanation, commute distance/time and CV reference.
  applications_log: prepared/submitted materials, CV version and application status.
- Matching/scoring: compare vacancies to a user profile and discard poor matches.
- CV preparation/renderer: prepare a targeted document and render it, for example
  through HTML/CSS-to-PDF or Typst.
- Reporting/notifications: a table/dashboard and optional Telegram/web notifications
  for manual review and submission.

3. Sources: API endpoints versus parsing

Portals change frontend/backend architecture and anti-bot controls; each source
needs a separate adapter with a clear contract.

JSON/REST/GraphQL:
Modern boards may load listings/details through public or internal JSON APIs or
feeds. Structured responses are simpler to process than HTML. Use correct headers,
rate limits, paging and schema-change handling. An internal endpoint is not
automatically a supported public contract.

HTML/headless browser:
The original proposal allowed Playwright for client-rendered pages and complex
filters, including parts of Pracuj.pl. The later decision postpones all HTML
scrapers and browser fallback; use APIs/structured RSS only in the current phase.

Geolocation/commute:
Future office/hybrid matching may extract city/district/coordinates and calculate
distance/time from the user's starting point through a geocoder and routing API,
such as OpenRouteService or Google Maps. Include the result in reports.

4. AI scoring and CV preparation

Matcher input: normalized vacancy + user profile.
Proposed JSON output: match_score (0–100), reasons_for_fit,
missing_skills_or_red_flags, salary_info, work_mode, location.
Do not spend CV-generation tokens on matches below the relevance threshold.

CV input: structured canonical CV + vacancy description.
The original future design allows reordering emphasis, rewriting experience bullets
in vacancy terminology, highlighting relevant projects/skills and adapting language
to Polish or English. Current code selects/reorders original facts only.
Never invent experience, companies, roles, certificates, years of experience or
skills absent from the canonical CV. Every fact must refer to the base profile.

5. Reporting and multi-user growth

Each selected vacancy should show position/company, direct URL, salary range and
contract (for example UoP/B2B), location/work mode (remote/hybrid/office), future
commute metrics, a generated CV and short change log, and a status:
New, Reviewed, Applied or Skipped.

Design user_id/tenant ownership from the start so profile uploads, filters and
queues can grow to multiple users without rewriting the core.
